# Decisions Log

Every assumption and ruling made while building this project. Newest phases append; earlier entries stay unless superseded.

## Fixed product decisions (from the brief, adopted as-is)

| # | Decision |
|---|----------|
| D1 | Money is stored and transported as integer cents. Currency is USD (`usd`). |
| D2 | Flat shipping fee and a free-shipping threshold are settings in the `settings` table (not env). Tax is a percentage setting, default `0`. |
| D3 | One `users` table with `type` = `customer` \| `staff`, separate customer/staff login endpoints and Sanctum abilities. Staff endpoints reject customer tokens and vice versa. |
| D4 | Sanctum bearer tokens are held only by the Next.js BFF in an httpOnly, Secure-capable, SameSite=Lax cookie. No token is ever sent to client JavaScript or localStorage. |
| D5 | Guest carts are identified by a UUID `cart_token` cookie and merged into the user cart on login. Checkout requires authentication. |
| D6 | No product variants. |
| D7 | Stripe PaymentIntent + signature-verified, idempotent webhook. Only the webhook marks an order paid. |
| D8 | Spatie Laravel Permission with guard-scoped roles; Super Admin bypasses checks with `Gate::before`. |
| D9 | Queue driver `database`; all mail queued; Mailpit locally. |
| D10 | MySQL `LIKE`/FULLTEXT search only. |

## P1 — Database, models, seeders

| # | Decision | Why | Cost if wrong |
|---|----------|-----|---------------|
| P1-1 | **No separate `addresses` table.** The shipping address is a denormalised snapshot on `orders`; the order policy guards access. | SEC-5 lists "addresses", but the required table list does not include an address book, and orders must never change when a saved address is edited. | If saved addresses become a requirement, add a `user_addresses` table later; order snapshots stay unchanged. |
| P1-2 | Coupon `value` is an **integer percentage (1–100)** for `percentage` coupons and **integer cents** for `fixed` coupons. | Avoids float money/percentage drift and keeps one integer column. | Percentages cannot be fractional (e.g. 12.5%). Acceptable for the brief; would become basis points later. |
| P1-3 | Soft deletes on `categories`, `products`, `coupons`; not on `orders`, `payments`, `users`. | Preserve catalogue history while keeping orders immutable and auditable. | A "deleted" product remains referenced by order snapshots. Admin lists must exclude trashed rows by default (P4/P7). |
| P1-4 | Cancelling a paid order **hard-deletes** the `coupon_usages` row and decrements `used_count` inside the same transaction. | Simple, exact restoration of both per-user and total limits. | Usage history for cancelled orders is lost; the order still stores `coupon_code` and discount. |
| P1-5 | Product images are generated locally with GD (`database/seeders/assets/generate-product-images.php`) and committed (~1 MB total). | NFR-SEED requires local images with no external dependency. | Repository is slightly larger. Regeneration is deterministic. |
| P1-6 | The cart stores `unit_price` when an item is added, so FR-CART-6 can flag price changes. Checkout always recalculates from products. | Detecting "price changed" needs the original price; it is never trusted as the charged price. | None; stale values are informational only. |
| P1-7 | Status/type columns are `string` + PHP backed enums, not MySQL `ENUM`. | Portable to SQLite tests, easy to extend, and still strictly cast. | Database-level enum validation is replaced by app validation/tests. |
| P1-8 | Settings keys are dotted (`shipping.flat_fee`, `tax.percent`, …) and typed (`string|integer|boolean|json`), cached through `SettingService`. | One place for every pricing input required by SEC-1. | A stale cache across processes is possible until `SettingService::flush()`; all writes go through the service. |
| P1-9 | Tests keep `BCRYPT_ROUNDS=12` (no test override), and a test asserts the hash cost. | SEC-2 says cost 12; testing the real cost is the evidence. | Slower test suite (~16s). |
| P1-10 | Seed passwords are inserted as plain strings and hashed by the model's `hashed` cast. | Exercises the same path used by the application and proves bcrypt is applied. | None. |
| P1-11 | `order_number_sequences` is a per-year counter; seeding and P6 both increment it under a transaction/lock. | FR-ORDER-9 requires a race-safe sequence. | Sequence gaps after failed transactions are acceptable (numbers need uniqueness, not density). |
| P1-12 | Seed orders do **not** decrement product stock. | The seed represents historical data, and stock values are curated to exercise all stock states. | Stock numbers are illustrative, not a ledger of seeded sales. Documented for reviewers. |

## P2 — Authentication

| # | Decision | Why | Cost if wrong |
|---|----------|-----|---------------|
| P2-1 | Login throttling is an explicit counter in `AuthService` keyed by `strtolower(email)|ip`, checked before credential validation, not route middleware. | FR-AUTH-5 counts *failed* attempts per email + IP; a generic route limiter would also count successes and cannot clear on success. | A distributed deployment needs a shared cache (the database cache is shared here). |
| P2-2 | Throttled responses are `429` with `Retry-After` and the standard envelope. | FR-AUTH-5 requires 429; the envelope keeps clients uniform. | None. |
| P2-3 | The password reset notification is queued (`ShouldQueue`), mirroring D9, and its link points at `FRONTEND_URL/reset-password?token=…&email=…`. | Mail must not block the request, and the frontend owns the reset screen (no Blade). | Local reviewers must run `queue:work` (or `queue:listen`) and Mailpit; documented in README. |
| P2-4 | `Password::uncompromised()` is enabled in every environment except tests (`PASSWORD_CHECK_PWNED=false` in `phpunit.xml`). The pwned path is still tested by one test that enables the rule and fakes the HaveIBeenPwned HTTP response. | The rule calls a public API; keeping it on in every test makes the suite network-dependent. | Tests do not exercise the live API; the faked test proves the rule is wired in. |
| P2-5 | Email verification (FR-AUTH-4) and staff TOTP 2FA (FR-AUTH-9) are **bonus** items and are deferred until all P0–P14 core work is complete. | They add flows (signed URLs, QR enrolment, recovery codes) that are not part of the core commerce journey. | The bonus points for those two items are not claimed unless time allows in P14. |
| P2-6 | Inactive users get the same generic `401` as a wrong password, and staff tokens are ability-scoped at the route level. | FR-AUTH-6 forbids enumeration; D3 requires separated surfaces. | Operators cannot distinguish a disabled account from bad credentials in the response — intentional; admins see `is_active` in the admin UI. |
| P2-7 | Sanctum caches the resolved guard user for the lifetime of a test; tests call `forgetAuthGuards()` after switching tokens. | Without it, sequential requests with different bearer tokens within one Pest test reuse the first user. | Test-only helper; real HTTP requests are unaffected. |

## P3 — RBAC

| # | Decision | Why | Cost if wrong |
|---|----------|-----|---------------|
| P3-1 | `Gate::before` short-circuits only **namespaced** permission abilities (those containing `.`), not bare policy abilities (`view`, `update`, `delete`). | FR-RBAC-4 gives Super Admin every permission but still forbids editing/deleting Super Admin accounts. A blanket bypass would defeat `StaffPolicy`. | Any future Gate ability intended for Super Admin must use the `domain.action` naming convention. Documented here and in `AppServiceProvider`. |
| P3-2 | `App\Models\Role` overrides Spatie's `users()` relation with an explicit `User` target. | After `auth:sanctum` authenticates, `auth.defaults.guard` becomes `sanctum`; Spatie's relation then looks for a provider-less guard and passes `null` to `morphedByMany`, breaking `withCount`/`loadCount` (500 on role list). | Role-model overrides must be kept in sync with Spatie upgrades. |
| P3-3 | Admin holds `staff.manage` but **not** `roles.manage`; only Super Admin sees the roles/permission matrix. Staff management by an Admin cannot grant the Super Admin role. | FR-RBAC-7 says the roles page is Super Admin only; staff operations are a normal admin duty. The escalation guard closes the obvious hole. | An Admin cannot create roles; a Super Admin must. |
| P3-4 | `DELETE /admin/staff/{id}` deactivates the account (and revokes tokens) instead of deleting the row. | Orders, status histories and activity logs reference the user; removing the row would corrupt the audit trail. | The API returns 204 like a delete, but the record persists. "Deleted" staff remain visible in filtered inactive lists. |
| P3-5 | Super Admin accounts are immutable through the staff API and staff cannot modify themselves. Combined with the immutable Super Admin role, this guarantees the last Super Admin can never be removed. | FR-RBAC-4 is an availability requirement: locking every admin out is worse than refusing a legitimate edit. | Renaming or resetting a Super Admin must be done directly in the database/console. There is always at least one working Super Admin. |
| P3-6 | Deleting a role still assigned to staff returns `409 Conflict`; the Super Admin role always returns `403`. | Deleting an in-use role would silently strip permissions; Spatie would detach users. The system role is not user-owned. | Admins must reassign staff before deleting a role. |
| P3-7 | `PermissionRegistry` (not the database) is the source of truth for permission names, labels and groups; the matrix API returns groups and roles in one response. | FR-RBAC-2/7 need a stable, ordered matrix; the seeder and UI both read the same list. | Adding a permission requires one registry entry plus a re-seed. |

## P4 — Catalog

| # | Decision | Why | Cost if wrong |
|---|----------|-----|---------------|
| P4-1 | Product descriptions are sanitized on write with **HTMLPurifier** (`ezyang/htmlpurifier`) using a small tag allowlist; no scripts, event handlers or `javascript:`/`data:` URLs. | SEC-4/FR-CAT-2; a hand-rolled regex sanitizer is not trustworthy. | One extra production dependency. Changing the allowlist requires re-saving old rows. |
| P4-2 | The effective price is the discount only when `discount_price < price`; both the model (`currentPrice`) and SQL (`CASE …`) apply that guard. | Protects sorting/filters from invalid legacy/imported rows, and keeps PHP and SQL ordering identical. | A malformed discount silently falls back to the regular price instead of showing a higher "sale" price. |
| P4-3 | Public product queries require `is_active` **and** an active non-deleted category; the category filter resolves the whole subtree in PHP from one category query. | FR-CAT-5 hides inactive products; the tree is small (3 levels) so one query plus in-memory traversal beats recursive SQL. | A very large category tree would need a materialized path/recursive CTE. |
| P4-4 | Deleting a category returns `409` when any child or product (including soft-deleted) still references it. | The FK would otherwise fail with a 500, and soft-deleted products still hold the reference. | Admins must move/delete products first. |
| P4-5 | Admin catalog routes bind by explicit `:id`; public product/category routes bind by slug. | Admin URLs stay stable while editors rename slugs; public URLs stay SEO-friendly. | Two binding conventions to remember. |
| P4-6 | Deleting a product soft-deletes the row but hard-deletes its image rows and files. | FR-CAT-6 requires file cleanup; the product snapshot in order items is independent. | Restoring a soft-deleted product does not restore its images; they must be re-uploaded. |
| P4-7 | Uploaded images use Laravel's hashed `store()` filename; the first image becomes primary automatically and deleting the primary promotes the next by `sort_order`. | FR-CAT-6 random names; the UI always has a primary image without a second request. | None. |
| P4-8 | Slugs are generated from the name when omitted, with `-2`, `-3` suffixes checked across soft-deleted rows; an explicit slug is honoured and validated as unique. | Avoids 500s from the unique index and keeps public URLs stable. | Renaming without an explicit slug changes the product URL (documented admin behaviour). |

## P5 — Cart and coupons

| # | Decision | Why | Cost if wrong |
|---|----------|-----|---------------|
| P5-1 | Guest identity travels as `X-Cart-Token` (preferred by the BFF) or the `cart_token` cookie; a new guest cart returns the token in `meta.cart_token` and sets an httpOnly 30-day cookie. | D5 requires a cookie token, but the Next.js BFF proxies server-side and cannot rely on cross-origin cookies; the header keeps both clients working. | Two transport paths to keep aligned; both are covered by the same service. |
| P5-2 | Totals include only available lines. Lines are still returned with `warnings` when the product was deactivated, its category was deactivated, stock ran out, stock fell below the quantity, or the price changed. The stored `unit_price` is never charged; `currentPrice()` is. | FR-CART-6 needs visibility, SEC-1 needs one authoritative price, and charging for an unavailable line would make the cart lie. | A cart can show a lower subtotal than the customer remembers; the warning explains why. Checkout revalidates anyway. |
| P5-3 | Adding beyond the cap/stock returns `422` with the maximum quantity; merging on login instead caps silently. | The customer is present when adding and deserves a reason; merging is automatic and has no prompt to answer. | A merge can reduce quantities without an explicit message (the cart response shows the result). |
| P5-4 | `CouponService` is shared by cart apply and (P6) checkout/payment. Per-user limits are checked only when a customer is authenticated; guest applies check every other rule. | FR-COUPON-2 requires revalidation at every step; a guest has no identity to count usages for. | A guest may apply a coupon they already used; checkout rejects it before payment. |
| P5-5 | Percentage discounts floor to whole cents and honour `max_discount_amount`; fixed discounts never exceed the subtotal. Shipping is free when the **post-discount** subtotal reaches the threshold; tax is computed on the post-discount merchandise subtotal. | One deterministic rule set for cart and order totals. | A large coupon can make shipping chargeable again; the cart shows the exact totals before checkout. |
| P5-6 | A coupon that becomes invalid between apply and read is detached from the cart automatically. | Quoting a discount the customer cannot get is worse than showing it removed. | The customer must re-enter a coupon that briefly lapsed; the cart always reflects reality. |
| P5-7 | Customer cart lines are resolved through the caller's cart (`whereKey` inside the cart), returning 404 for foreign ids; staff/non-customer tokens get 403. | SEC-5 IDOR requirement and D3 surface separation, without leaking whether an item exists. | None; the owner path is unchanged. |

## P6 — Checkout, payment, orders

| # | Decision | Why | Cost if wrong |
|---|----------|-----|---------------|
| P6-1 | Stripe sits behind `App\Support\Stripe\StripeGateway`; `StripeSdkGateway` is bound in production and `FakeStripeGateway` in tests. | FR-ORDER tests must cover success, decline, refunds and oversell deterministically without network calls. | A gateway bug would only surface in the live Stripe smoke test, not the suite. |
| P6-2 | `POST /checkout` reads `Idempotency-Key`; an empty header falls back to a random `auto-<uuid>`. The key is stored in `orders.checkout_idempotency_key` with a unique index and returns the existing order/intent on a repeat. | FR-ORDER-3 requires idempotency; retries must never double-charge or create duplicate orders. | A client that loses its key creates a second pending order (the first is later expired). |
| P6-3 | The order and items are created inside a transaction, then the PaymentIntent is requested with `order-{id}-payment`, and only then is the cart emptied. | If Stripe fails, the transaction rolls back and the customer keeps the cart; retrying reuses the same Stripe idempotency key. | A Stripe timeout can leave locks held until the transaction ends. |
| P6-4 | Order numbers come from a locked row in `order_number_sequences` (`ORD-YYYY-NNNNNN`). | FR-ORDER-9 needs a readable, race-safe sequence; `count()+1` would collide under concurrency. | One extra row per year and a short lock on allocation. |
| P6-5 | The webhook verifies the raw-body signature before JSON parsing, then stores the event id and processes it in one transaction. A duplicate id is ignored before any side effect. | FR-ORDER-7; parsing untrusted JSON first would defeat the point of the signature and duplicate events must not decrement stock twice. | Stripe retries of an event whose transaction failed are stored but not processed; the event must be replayed manually. |
| P6-6 | Only a `pending` order can become paid. The paid handler rechecks the paid amount, coupon validity and stock under `lockForUpdate`; any failure refunds, cancels and records the reason. | FR-ORDER-5/8: payment can succeed after the cart changed, so the webhook, not checkout, owns stock and coupon side effects. | A refund is issued for a genuinely paid order when the coupon expired in the payment window; the message explains why. |
| P6-7 | Refund and PaymentIntent cancellation calls run inside the DB transaction that changes the order/payment. | Simpler than an outbox in this phase and keeps local state consistent in the common case. | A Stripe outage can hold locks or roll back a local cancel after Stripe accepted the refund; provider calls are idempotency-keyed so a retry is safe. |
| P6-8 | Cancelling `pending` only releases the PaymentIntent; cancelling a paid order refunds, restores stock and removes coupon usage. The hourly `orders:expire-pending` command uses the same transition path with a configurable window. | FR-ORDER-12/14; one cancellation path prevents divergent stock/coupon behaviour. | Orders paid after an expiry race are ignored by the webhook and need a manual refund check in Stripe. |
| P6-9 | Customer orders are authorized by `OrderPolicy`; a denied `view` is converted to 404. The list query is scoped to the authenticated user. | FR-ORDER-13/SEC-5: foreign ids must not be probeable, and a policy keeps the rule testable. | None; admins use the P7 admin endpoints, not this controller. |
| P6-10 | Checkout rejects grand totals below 50 cents, and a coupon is snapshotted on the order only when it produced a discount. | Stripe's minimum charge is 50 cents; a zero-discount coupon should not consume usage or block cancellation. | A free order cannot be paid by card; a future free-checkout flow needs its own path. |

## P7 — Admin API

| # | Decision | Why | Cost if wrong |
|---|----------|-----|---------------|
| P7-1 | The admin status endpoint never accepts `paid`; only the verified Stripe webhook transitions an order to paid. | Payment truth must come from Stripe (FR-ORDER-5), otherwise staff could mark unpaid orders paid and ship goods. | An order whose webhook is lost must be reconciled in Stripe and replayed, not fixed by hand. |
| P7-2 | `valid_transitions` is computed server-side by `OrderService`/`OrderStatus` and filtered so `paid` never appears in the admin UI. | The client should render actions the server will actually allow; duplicating the table in TypeScript would drift. | Adding a new status requires only the backend enum/table to change. |
| P7-3 | Cancelling an order requires both `orders.update_status` and `orders.cancel`; the controller checks the latter only when the target is `cancelled`. | Fulfilment staff can progress orders without being able to trigger refunds and stock restores. | A custom role that should cancel must be granted `orders.cancel` explicitly. |
| P7-4 | Customers are read only through `type=customer`; a staff id on `/admin/customers/{id}` is a 404, and customer tokens never reach the admin group. | D3 surface separation and SEC-5: the admin customer screen must not leak staff accounts or accept customer credentials. | Staff profiles are managed by P3's `admin/staff` endpoints instead. |
| P7-5 | Coupon codes are normalised (trim + uppercase) in the FormRequest; percentage values are capped at 100; duplicate codes are rejected case-insensitively through the normalised value. | Coupons are entered by humans and matched against uppercased checkout codes; one representation avoids near-duplicates. | A coupon created with lowercase input is stored uppercase; the API response shows the canonical form. |
| P7-6 | Coupon update uses the same FormRequest as create (full representation) rather than partial validation. | One rule set for value/type/expiry keeps the money rules in a single place; the admin form submits every editable field. | A PATCH that omits `code`/`type`/`value` is a 422. |
| P7-7 | Staff self-service edits only name, phone and email; changing email clears `email_verified_at`, and password changes stay on the dedicated auth endpoint with the current password. | `type`, `is_active` and roles are privileged (SEC-6); separating password change keeps re-authentication and token revocation in `AuthService`. | A staff member cannot change their own role or reactivate themselves; a Super Admin must do it. |
| P7-8 | Activity logging is best-effort: `ActivityLogger` runs in `rescue(..., report: true)` after the business action commits. The read endpoint is gated by the existing `roles.manage` permission instead of a new `activity.view`. | An audit write must never fail a refund or status change; reusing `roles.manage` avoids expanding the permission matrix for a bonus feature. | A failed log is reported but the action still succeeds; only Super Admins can read the trail. |
| P7-9 | The dashboard's 30-day series is zero-filled in PHP and grouped by `DATE(paid_at)`; revenue counts paid-family statuses only, and "today's orders" counts orders created today regardless of status. | The chart should show a continuous 30-day window, and revenue must mean captured money while order volume means demand. | Two different date bases (created vs paid) appear on one screen; the labels in the response make the distinction explicit. |
| P7-10 | `AdminPermissionTest` drives every protected route with three identities (guest, customer token, role-less staff) and the profile route with a role-less staff token. | A single table-driven test prevents a new admin route from shipping without auth/permission middleware. | New endpoints must be added to the table when introduced, or the safety net silently misses them. |

## P8 — Frontend foundation

| # | Decision | Why | Cost if wrong |
|---|----------|-----|---------------|
| P8-1 | With no Figma file supplied, the `ui/` storefront template is the design source. Only its visual language (tokens, typography, spacing, card shapes, images) is ported; its antd components and mock data are not. | FR-UI-2 needs a concrete reference, and the template already matches the SHOP.CO-style direction. Keeping mock data out avoids a second source of truth. | If the reviewer expects the exact Figma, colours/spacing may differ; P9 pages reuse the shell so a token change is cheap. |
| P8-2 | Route protection and CSP live in `src/proxy.ts`, Next 16's renamed middleware, not `middleware.ts`. | Next 16 rejects the old filename/behaviour; the bundled docs define proxy as the supported hook. | None; the exported matcher and function names are the documented ones. |
| P8-3 | The BFF stores the Laravel bearer token in an httpOnly cookie and proxies `/api/auth/*` and `/api/admin/auth/*`; the browser never receives the token. | P8 DoD and FR-AUTH: localStorage would expose the token to XSS. The API remains a pure bearer API. | Server-side pages must read the session through the BFF helper; client components cannot call the Laravel API directly with credentials (by design). |
| P8-4 | Session cookies are `SameSite=Lax`, httpOnly, path-wide, and `Secure` only when `COOKIE_SECURE=true`; every state-changing BFF call checks the `Origin` against the request origin plus `NEXT_PUBLIC_SITE_URL`. | SEC-9 asks for SameSite plus origin checks because the BFF is cookie-authenticated. A blanket `Strict` policy would break links from email into the storefront. | A same-site subdomain that is compromised could still send state-changing requests; no CORS origin is trusted by default. |
| P8-5 | Auth cookies are separate per surface (`nocfinity_token`, `nocfinity_admin_token`), and guards only accept the matching cookie. Logging out of one surface does not clear the other. | D3 separates customer and staff surfaces; a customer token must never unlock `/admin`, even optimistically. | Staff can hold both sessions in one browser; the API still rejects the wrong ability per route. |
| P8-6 | Session-dependent UI is a server component inside `<Suspense>`; the static shell renders immediately with a skeleton. | Cache Components enabled in Next 16 cannot prerender cookie reads; Suspense keeps the shell partial-prerendered and avoids build failures. | Pages that read `cookies()` outside Suspense fail the build; the pattern is documented in P8's report. |
| P8-7 | The login form validates locally (required fields + email format) but treats the Laravel response as the source of truth, mapping `errors` onto fields and preserving `Retry-After` on 429. | SEC-14 requires both sides; duplicating password policy in the browser would drift from the backend. | A weak password reaches the API and comes back as a field error; that is acceptable and consistent. |
| P8-8 | CSP is per-request with a nonce and `strict-dynamic`, attached in the proxy; static security headers stay in `next.config.ts` and HSTS is production-only. | One CSP needs a fresh nonce per document, while HSTS over plain-HTTP local development would brick `localhost`. | The proxy adds a small per-request cost; a future static-only deployment would need another nonce source. |





## P9 — Storefront pages

| # | Decision | Why | Cost if wrong |
|---|----------|-----|---------------|
| P9-1 | Storefront pages are server components that read the API through `apiFetch`/`createCatalogApi` inside `<Suspense>`; only the cart controller, quantity steppers and the gallery are client components. | Cache Components cannot prerender cookie-bound data, and catalogue content must be server-rendered for FR-UI-4. | Any new page that reads session/cart state must keep its Suspense boundary or the build fails. |
| P9-2 | The listing URL is the single source of truth for filters; shoppers type dollars in the query string while the API always receives integer cents, and invalid or oversized values fall back to defaults. | FR-CAT-3 needs shareable, bookmarkable filters and one unit per boundary; the URL survives reloads and back/forward. | A link with `sort=popular` silently shows newest rather than reporting an error. |
| P9-3 | Cart mutations go through the BFF routes under `/api/cart*`; the guest `cart_token` stays httpOnly and every mutation returns the full recalculated cart, which the client adopts before `router.refresh()`. | The backend owns money (SEC-1) and the token must stay out of JavaScript (P8-3); returning the whole cart avoids a second totals implementation in the browser. | The header badge can lag one refresh behind the line items until the RSC payload lands. |
| P9-4 | `on_sale=1` was added to the public product index (`discount_price IS NOT NULL AND discount_price < price`) and exposed as a listing checkbox, instead of leaving the header's sale link to be ignored by the API. | The shell already advertises an "On Sale" destination and the seeded catalogue has discounted products; a nav link that silently returns everything is a defect. | "On sale" means "has a discount price", not a scheduled campaign window; dated promotions need a later field. |
| P9-5 | Product descriptions are rendered as plain text with preserved line breaks, not as HTML. | Descriptions are sanitized on write, but rendering raw HTML would make the storefront depend on the allowlist staying correct forever. | Rich formatting (bold, lists) written by admins is flattened on the detail page. |
| P9-6 | Listing prices are sent as `min_price`/`max_price` independently; the FormRequest only requires `gte:min_price` when both are present. | The UI exposes min and max as separate optional fields, and the previous rule rejected a max-only range, which broke the "Under $100" links. | A max-only request is no longer rejected; the service applies whichever bound exists. |

## P10 — Checkout and account pages

| # | Decision | Why | Cost if wrong |
|---|----------|-----|---------------|
| P10-1 | Checkout is two steps: the address form first creates a `pending` order plus PaymentIntent through `POST /api/checkout`, then Stripe Elements mounts with that `client_secret`. The browser keeps one `crypto.randomUUID()` per attempt in the `Idempotency-Key` header. | Stripe Elements needs a PaymentIntent, and FR-ORDER-2/3 require the amount to be calculated before payment. The stable key makes a retried submit return the existing order instead of charging twice. | Reloading after the order is created leaves an unpaid order that expires after 60 minutes (`orders:expire-pending`). |
| P10-2 | Confirmation lives at `/checkout/confirmation/[order]`, renders the real order, and shows "Confirming your payment" while the status is `pending`. | FR-ORDER-7 makes the webhook the only source of `paid`; the page must not claim success from a redirect. Refreshing is enough because the webhook normally lands within seconds. | A slow webhook means the customer sees the pending state until they refresh. |
| P10-3 | My Orders (`/account/orders`) and order detail (`/account/orders/[order]`) read through `apiFetch` with the session token inside `<Suspense>`, page through `?page=`. | Keeps the bearer token server-side and avoids another BFF surface for read-only data. | Pagination state is a query param, so the page is not cached on the client; that is fine for account data. |
| P10-4 | Customers cancel through `POST /api/v1/orders/{order}/cancel`, guarded by `OrderPolicy::cancel` (owner + `isCancellable`) and executed by `OrderService::transition`, so refunds, stock restoration and coupon restoration stay in one place. A foreign order is 404; a non-cancellable one is 422. | FR-ORDER-12 already defines the side effects; a second cancel path would duplicate them and risk double refunds. | Customers can cancel `pending`, `paid` and `processing` orders, including triggering a refund; shipping and later states are refused. |
| P10-5 | Guest-cart merge now also runs on registration, not just login, and the BFF forwards the httpOnly cart token as `X-Cart-Token` on both calls. | Registration signs the customer straight in (auto-login), so treating it differently from login would silently drop the guest cart. | A customer who registers instead of logging in keeps the same cart; the stale guest cookie is harmless because the backend deletes the guest cart during the merge. |
| P10-6 | Stripe is configured only through `NEXT_PUBLIC_STRIPE_PUBLISHABLE_KEY` (browser) and `STRIPE_KEY`/`STRIPE_SECRET` (Laravel); a missing publishable key renders a setup notice instead of a broken payment form. The CSP allows `https://js.stripe.com` in `script-src` and `https://m.stripe.network` in `frame-src`. | Card data must never touch our servers (SEC-12), and `strict-dynamic` alone would block Stripe.js. | The local environment currently has all three values empty, so the live success/decline run is blocked until they are filled in. |
| P10-7 | A missing or foreign order renders the storefront not-found UI inside the streamed boundary with `robots: noindex`, which is HTTP 200 at the transport level. Ownership is still enforced by the API (404) and no order data is rendered. | Same Cache Components constraint documented in P9-6 for products: resolving the order before the shell would disable partial prerendering. | A crawler sees 200 for a foreign/deleted order URL, so the noindex tag is what prevents indexing. |

## P11 — Admin panel UI

| # | Decision | Why | Cost if wrong |
|---|----------|-----|---------------|
| P11-1 | Admin mutations use one BFF catch-all, `/api/admin/[...path]`, that forwards method, query, JSON or multipart bytes and the httpOnly staff bearer to Laravel. Reads stay in server components through `adminGet`. | One proxy keeps the token server-side (D4/P8-3), supports image uploads without a second client, and leaves every authorization decision with the Laravel permission middleware. | A new admin endpoint needs no new Next route, so the BFF surface is broader than a per-resource handler; the origin check and backend permissions are the guardrails. |
| P11-2 | `adminGet` returns `{ok, status, message}` instead of throwing, and screens render a 403/retry panel; mutations use `adminRequest` from the browser and then `router.refresh()`. | Cache Components needs server reads inside Suspense, and a denied permission should explain itself rather than hit the error boundary. Refresh re-runs the server read so tables never hold stale server data. | A screen waits for a full RSC round trip after each mutation instead of updating optimistically. |
| P11-3 | Menu items are gated by the permission names the API actually uses (`products.view`, `categories.manage`, `orders.view`, `coupons.manage`, `customers.view`, `reports.view`, `staff.manage`, `roles.manage`), and action buttons are hidden the same way. | FR-RBAC-6 requires the UI to hide what the token cannot do. The previous `categories.view` gate was a permission that does not exist, so Product Managers could manage categories through the API but never saw the menu. | Hiding a button is cosmetic only; the API remains the authority and still returns 403. |
| P11-4 | Product prices and fixed coupon values are edited in dollars and converted to integer cents at the submit boundary; discount prices are validated against the price in the browser before the API revalidates. | D1 stores cents and the API validates them; admins should not type cents. | Rounding uses `Math.round`, so a third decimal is lost — acceptable for a cents-only schema. |
| P11-5 | Order status actions are built from the server's `valid_transitions`, exclude `paid`, and drop `cancelled` unless the staff member holds `orders.cancel`. | FR-ADMIN-4 and FR-ORDER-5/12: the transition table and refund permission live on the server; duplicating them in the UI would drift. | A staff member without `orders.cancel` sees no cancel option and the API would refuse it anyway. |
| P11-6 | The permission matrix saves only roles whose checkbox set changed, renders the Super Admin column read-only, and creates custom roles with an empty permission set. | FR-RBAC-4 keeps the system role immutable, and sending every role on each save would overwrite concurrent edits from another administrator. | Two administrators editing different roles at once is safe; editing the same role last-write-wins. |
| P11-7 | When the role catalogue cannot be read (an Admin has `staff.manage` but not `roles.manage`), the staff form derives its role options from the roles already assigned to staff and shows a note. | The role index API is deliberately Super-Admin-only and its test asserts 403 without `roles.manage`; blocking the whole staff screen would make `staff.manage` unusable for Admins. | A role with no staff members is not offered in that fallback; a Super Admin sees the full catalogue. |
| P11-8 | Dark mode is a localStorage class toggle mounted in the admin sidebar, read through `useSyncExternalStore`, rather than a global theme provider. | The bonus only asks for an admin toggle, and a provider would need a nonce-aware pre-paint script under the strict CSP. | Once toggled the `dark` class is global, so storefront pages in the same tab also render dark until it is switched back. |
| P11-9 | A read-only activity-log screen was added at `/admin/activity-logs`, gated by `roles.manage`. | The P8 sidebar already linked to that URL and the P7 API exists, so leaving it as a 404 would be a dead menu entry (FR-ADMIN-10 bonus). | The log is append-only and unbounded, so it needs a retention policy before production (P12/P14). |

## P11 follow-up — Docker Compose

| # | Decision | Why | Cost if wrong |
|---|----------|-----|---------------|
| P11-D1 | The API container runs `php artisan serve` on PHP 8.4 CLI instead of a separate PHP-FPM + nginx pair. | The OPS-5 bonus asks for a one-command local run; one process per role keeps the Compose graph small and matches the documented local workflow. | It is a development server: no production concurrency or TLS termination. `docs/DOCKER.md` states this and a production stack would add nginx/FPM. |
| P11-D2 | The Next container talks to `http://backend:8000/api/v1`, while `API_PUBLIC_ORIGIN=http://localhost:8000` is used for the CSP and `NEXT_IMAGE_UNOPTIMIZED=true` is set in Compose. | Inside the network the service name is the API, but the browser and the image optimizer resolve different hosts; without the split, the CSP would block product images and `next/image` would 500. | The CSP env var adds one optional setting; images are served at original size in Docker only. |
| P11-D3 | Compose passes all configuration as environment variables and never copies `backend/.env` (or `frontend/.env.local`) into an image; the entrypoint seeds only when the users table is empty. | Host env files hold real local credentials, and unconditional re-seeding would reset stock/catalogue edits on every restart. | A container recreated with a new `APP_KEY` would invalidate sessions; the compose file pins a local-only key so sessions survive. |
| P11-D4 | MySQL is published on `3307` and Mailpit UI on `8025`, both overridable, and only the API container runs migrations (`RUN_MIGRATIONS=false` for queue/scheduler). | The developer machine already runs MySQL on 3306 and Mailpit on 8025, and three containers racing migrations on boot would be flaky. | Changing the published API/app ports requires a frontend rebuild because public URLs are baked at build time. |

## P12 — Security hardening

| # | Decision | Why | Cost if wrong |
|---|----------|-----|---------------|
| P12-1 | New checks live in `backend/tests/Feature/Security/` (injection, transport, data exposure, rate limits) and reference the existing tampering/IDOR/auth suites instead of duplicating them. | 180 tests already covered cart/checkout tampering, ownership, per-route throttles and model mass assignment; P12 needed the missing API-edge cases, not a second copy. | The evidence table in `SECURITY.md` spans several files, so a reviewer must follow links rather than read one suite. |
| P12-2 | The CORS allowlist test configures **two** origins. | `fruitcake/php-cors` emits a single allowed origin verbatim for every response; browsers still compare it to their own origin, so the header alone proves nothing. Two origins force the dynamic `isOriginAllowed` branch and let the test assert that a foreign origin gets no header at all. | The single-origin production case is not exercised by that assertion; the library behaviour is documented in `SECURITY.md`. |
| P12-3 | HSTS is added by `SecurityHeaders` only when `$request->isSecure()`; trusted proxies are not enabled in the repository. | Local development runs plain HTTP and an unconditional HSTS header would pin `localhost` to HTTPS. A TLS-terminating proxy must configure `TrustProxies`, otherwise Laravel never sees the request as secure. | Behind an unconfigured proxy the deployed API omits HSTS even over HTTPS; the production checklist calls this out. |
| P12-4 | Product JSON-LD is serialized with `serializeJsonLd()` (escapes `<` to `\u003c`) instead of `JSON.stringify`. | The page uses `dangerouslySetInnerHTML`; a product name or description containing `</script>` could otherwise end the script element and inject markup (SEC-4). Escaping `<` keeps valid JSON and neutralizes the sequence. | JSON-LD values are unchanged after parsing; only the on-wire representation differs. |
| P12-5 | The 4 moderate npm advisories (`minimatch` via `shadcn`/`ts-morph`) are accepted and documented rather than fixed with `npm audit fix --force`. | They affect build-time tooling only, are absent from `npm audit --omit=dev`, and the only automated fix downgrades `shadcn` to 1.0.0 (breaking). | A compromised dev-tooling input could cause a DoS during a schema-generation step; production runtime is unaffected. |
| P12-6 | Rate-limit tests send intentionally invalid requests (empty checkout carts) and assert the 429 on the 11th/121st call. | The limiter runs before validation/controllers, so the status change is observable without mocking Stripe or creating 120 real orders. | The test proves the counter, not that a successful checkout is also blocked; the middleware wraps the same route either way. |

## P13 — Testing and bug fixing

| # | Decision | Why | Cost if wrong |
|---|----------|-----|---------------|
| P13-1 | Checkout idempotency is unique per `(user_id, checkout_idempotency_key)`, not globally. A new migration replaces the original global unique index. | The service already scoped its lookup by user, so a customer reusing a key that another customer had used hit a database unique violation (500) instead of creating or resuming their own order. | Two customers can now hold the same key string; that is the intended meaning of a client-generated idempotency key. |
| P13-2 | The test suite stays on SQLite in memory; no DB-level concurrency/load tests were added. | The suite must run anywhere without services, and oversell is already covered behaviourally: products lock in id order and a payment that can no longer be fulfilled is refunded and cancelled. | A true simultaneous-checkout race is not reproduced in CI; production correctness relies on `lockForUpdate` and the webhook refund path. |
| P13-3 | A regression test asserts stock does not move until payment succeeds, and that idempotency keys are per customer. | Both are easy to break silently (a moved decrement or a changed unique index) and both affect money/ownership. | Two extra checkout tests add ~0.9s to the suite. |
